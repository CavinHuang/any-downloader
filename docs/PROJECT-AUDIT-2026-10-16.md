# 项目代码与用户交互审查

日期：2026-10-16。对象：当前工作区，包含桌面端和浏览器扩展的界面改版。

本次沿任务创建、下载、暂停恢复、落盘、桌面状态同步、扩展通信和文章同步链路进行静态检查，并针对疑点运行隔离复现。它不是逐行覆盖全部源码、真实站点兼容性认证或安装包验收。

## 判断与优先顺序

下一轮应优先让任务行为、设置和反馈保持一致。现有模块拆分、下载校验、断点记录及大量适配器测试可以保留；发现的问题主要集中在跨模块的接线、生命周期和协议边界。

P1 表示会造成常用操作失效、任务卡住或约束被绕过，应优先修复；P2 表示反馈、完整性和特定场景的可靠性问题，随后处理。以下问题均尚未在本次审查中修改业务实现。

## 缺陷明细

### F01：把任务调度收回引擎统一管理

位置：`src-tauri/src/commands.rs:94`、`crates/dl-ipc/src/ipc.rs:284`、`crates/dl-engine/src/engine.rs:131`。

桌面命令检查 `running_count()`，达到上限直接返回错误；扩展的 `task.start` 直接创建下载任务，未执行该检查，也没有桌面入口的任务级自动重试循环。真实 IPC 复现中，将 `max_concurrent` 设为 1，启动两个任务后观察到运行数为 2。

桌面的检查与实际启动之间还有异步间隔，多个同时到达的调用可能一起通过。批量添加先创建记录、再请求启动，超过上限时会留下没有自动递补的排队任务；用户看到的是部分失败。详情中的优先级主要作用于 CLI 的 `run_queued`，常用桌面和扩展入口没有持续队列调度。

建议：引擎提供统一的提交、排队、占用槽位和取消接口，统一执行优先级、并发和重试；桌面、IPC、CLI 共享。提交成功返回“已排队”，真正开始通过状态事件通知。引擎内同任务运行检查与 `runs.insert` 也应在一个原子临界区内完成，防止并发启动覆盖控制句柄。

验收：上限为 1，分别从桌面和扩展同时提交多个任务，始终只执行 1 个；结束后按优先级递补；各入口重试行为相同。

### F02：限速为 0 会耗尽额度后停住

位置：`ui/src/components/SettingsDialog.tsx:239`、`crates/dl-engine/src/engine.rs:555`、`crates/dl-throttle/src/lib.rs:56`。

输入允许 0，输入框占位符也是 0。后端把字符串 `"0"` 解析为 `Some(0)`，并创建补充速率为 0 的令牌桶。复现中，全局桶初始 1 MiB 额度用完后，下一次申请无法完成。单任务桶也存在同类问题。界面文字写的是“留空不限”，但没有拒绝 0，也没有解释 0 会停止传输。

建议：确定统一语义，优先将 0 和留空都归一为不限速；或拒绝 0，要求正整数。归一逻辑必须位于所有入口共用的引擎层。

验收：分别保存空值、0 和正常正整数，下载超过初始突发容量，确认行为符合界面说明。

### F03：全局限速没有在任务之间共享

位置：`crates/dl-engine/src/driver.rs:267`、`crates/dl-throttle/src/lib.rs:56`、`crates/dl-engine/src/hls.rs:202`、`crates/dl-engine/src/ytdlp_task.rs`。

每次启动下载都创建一个新的 `Limiter`，其“全局桶”只在当前任务内共享。原生测试同时下载两个 4 MiB 文件，全局设置 1 MiB/s，合计 8 MiB 在约 3.28 秒完成；这一观察与每个任务拥有独立桶的代码一致。HLS 分片直接读取响应体，未使用 `ctx.limiter`；yt-dlp 参数目前只透传单任务限速。

建议：由引擎持有共享的全局预算，各任务再派生自己的预算。HLS 使用流式读取并纳入限速；对托管下载器明确支持范围，并实现统一预算分配或明确界面限制。

验收：多任务运行时，允许明确的启动突发，但持续合计吞吐受全局设置约束；覆盖 HTTP、HLS 和托管下载。

### F04：恢复操作造成“正在下载”的假状态

位置：`crates/dl-ipc/src/ipc.rs:335`、`crates/dl-engine/src/engine.rs:610`、`crates/dl-cli/src/main.rs:309`。

`task.resume` 调用 `engine.resume()`，后者只迁移到 `Downloading`。原生复现先真正下载并暂停，再通过命名管道恢复，响应成功、记录状态为 `downloading`，但 `running_count()` 为 0。桌面按钮使用另一条启动路径，因此现有桌面正常操作不能证明 CLI 恢复可用。

建议：恢复应进入统一调度入口并实际启动驱动，状态随驱动变化。只改变状态的内部方法不应直接暴露成用户操作。

### F05：重命名存在两层缺口

位置：`ui/src/api.ts:121`、`src-tauri/src/main.rs:204`、`crates/dl-engine/src/engine.rs:639`。

前端调用 `rename_task`，Tauri 注册列表缺少该命令。即使补上接线，底层目前也只更新数据库。真实文件复现中，完成的 `before.md` 被改名为 `after.md` 后，记录显示新名，磁盘仍只有旧文件；后续“打开”会找不到记录中的路径并退回目录。

暂停任务的 `.dlpart` 也依赖文件名。应同时梳理临时文件和断点元数据的改名，避免丢失续传路径。

建议：分别定义未启动、暂停、完成任务的改名行为；执行磁盘冲突检查与移动，失败时保留原记录。补上命令注册、真实文件测试和原生接口契约检查。

### F06：等待响应的网络请求缺少取消边界

位置：`crates/dl-net/src/client.rs:12`、`crates/dl-net/src/probe.rs:37`、`crates/dl-engine/src/driver.rs:376`、`crates/dl-engine/src/hls.rs:202`。

客户端设置了连接超时，但未设置等待响应头和完整响应的统一超时。主源探测直接等待请求完成，暂停标记只在探测返回后检查。本地服务器接受连接但不返回响应时，请求暂停后任务仍停在 `probing`，驱动没有退出；复现等待 500 ms 仍未完成，代码路径也没有后续的响应截止时间。

HTTP 下载块读取已有停滞超时，但它覆盖不到探测和等待响应头；HLS 读取完整分片也应一并处理。

建议：分别设置连接、响应头和传输停滞超时，所有网络阶段都选择等待“响应 / 超时 / 取消”。托盘退出目前固定等 800 ms，应改为等待驱动真正结束并设置明确的退出截止策略。

### F07：HLS 进度上报没有跟随任务生命周期结束

位置：`crates/dl-engine/src/hls.rs:360`。

进度上报通过独立 `spawn` 启动，退出条件只有全部分片完成；失败、取消或暂停时，未完成分片数不会达到总数，也没有取消条件或回收句柄。真实分片失败复现中，任务已是 `failed`，之后仍捕获到该任务的 6 条进度事件。

这会保留后台循环、继续发送过期进度，且定期写入任务数据；重复恢复可能叠加上报任务。前端 `applyEvent` 对进度事件没有终态防护，会进一步放大旧事件的影响。

建议：将报告器、分片工作者纳入同一生命周期，所有结束路径取消并等待报告器退出；前端拒绝结束状态的迟到进度。

### F08：桌面增量刷新可能永远错过数据

位置：`ui/src/store.ts:54`、`crates/dl-persist/src/lib.rs:415`、`crates/dl-persist/src/lib.rs:437`。

全量响应到达后，以前端此时的 `Date.now()` 作为后续游标。复现模拟列表在 1000 ms 取得旧快照、1400 ms 发生更新、2000 ms 收到旧快照；后续查询从 1950 ms 开始，1400 ms 的更新被漏掉。50 ms 回看无法覆盖较长的请求耗时，也无法解决端点时钟差异。

另外，增量接口只返回现有记录，直接删除没有墓碑或删除事件。从 CLI 或其他客户端删除后，桌面仍保留旧记录，直到手动全量刷新。

建议：使用后端一致性快照游标或递增变更序号，包含删除标记；全量和增量的并发响应也应有版本保护。周期性全量对账可作为短期补救。

### F09：扩展任务列表会超出协议容量

位置：`crates/dl-ipc/src/ipc.rs:12`、`crates/dl-ipc/src/ipc.rs:223`、`extension/popup.js:610`。

`task.list` 返回全部完整任务；扩展取得响应后才截取 30 条。10000 条不含敏感请求头的简化完整记录，序列化约 4.24 MB，已超过接收端的 1 MiB 上限。实际帧写入器接受超限载荷，实际读取器随后返回 `frame exceeds limit`。任务越多，扩展反而可能持续显示离线。

建议：后端提供分页与字段精简的列表接口，明确最近任务排序；写帧前校验大小并返回可读错误。不要仅增大本地读取上限，因为扩展方向的容量约束仍然存在。

### F10：扩展按钮把失败吞掉了

位置：`extension/popup.js:538`。

按钮处理只等待 `send()`，没有判断返回对象的 `ok`。服务返回 `{ok:false,error:...}` 时，用户没有看到错误。若传输直接抛出异常，处理器虽然添加错误元素，接下来的 `renderTasks()` 又重建列表并立即清除错误。浏览器页面中两种情况均已复现。

建议：统一解析操作结果，保留独立于列表刷新的消息区，并在操作中禁用重复点击。区分“已接收 / 已排队 / 开始执行 / 执行失败”。

### F11：完成后动作没有实际执行

位置：`ui/src/components/SettingsDialog.tsx:278`、`src-tauri/src/commands.rs:189`、`src-tauri/src/main.rs:135`。

界面提供打开文件、打开目录、关机和休眠，设置可以存取；完成事件当前只发送通知，没有读取和执行 `after_done` 的代码。

建议：明确这些动作按“单任务完成”还是“整个队列完成”触发，再实现对应流程。关机和休眠需要清晰的触发说明、倒计时和取消入口；实现前应避免让未生效的选项表现为可用能力。

### F12：文章账号保存失败仍提示成功

位置：`extension/sync/engine.js:31`、`extension/sync/engine.js:256`、`extension/sync/sync.js:396`。

`storageSet` 吞掉写入异常。模拟存储不可用后，`saveCmsAccount` 仍返回账号对象，实际账号列表为空；界面会继续显示“账号已保存”。账号信息和密码还分两次写入，存在只写入一部分的可能。历史保存和清空也使用同一静默接口。

建议：关键持久化失败向调用方传播，一次提交关联数据；界面只在确认写入后提示成功。缓存等可降级的写入可以单独保留容错。

### F13：取消同步后，部分平台没有最终状态

位置：`extension/sync/engine.js:189`、`extension/sync/sync.js:222`。

取消时，尚未开始的一批只追加“已取消”结果，没有调用进度回调。复现选 4 个平台，在第一批取消后，第 4 个平台有取消结果却没有状态回调，页面对应行仍显示“待同步”。页面最终统一提示“同步完成”，也没有区分用户取消。

建议：每个平台都发出明确终态；区分取消与失败，并提供“仅重试失败项”。同时让单平台超时中止实际请求，避免仅结束等待、底层发布仍在继续。

### F14：速度和大小展示应统一单位

位置：`ui/src/store.ts:104`、`ui/src/components/TaskRow.tsx:112`、`ui/src/App.tsx:98`。

分段速度要求相邻采样间隔大于 200 ms，但每次事件都会重置时间。实际数据仓输入连续 100 ms 事件后，分段速度始终为 `null`。应累积到采样窗口再计算，而非每个事件重置基线。

HLS 的 `total_bytes` 实际装的是分片数量。完成态顶部摘要直接调用 `fmtBytes(total)`，会把 120 个分片显示为 120 B；同一行下方却按分片展示。任务栏汇总也把 HTTP 字节和 HLS 分片相加。应使用明确的进度单位类型，并将最终文件大小独立记录。这一项也覆盖了前面的界面改版，需要纳入修复。

### F15：现有自动检查覆盖不到这些边界

位置：`.github/workflows/ci.yml`、`ui/package.json:8`、`scripts/test_ui_store.cjs`、`ui/package-lock.json:26`。

CI 构建 UI 并运行 Rust 检查与测试，但没有执行 6 套扩展 JavaScript 测试、数据仓测试或 `tsc --noEmit`；当前 `build` 仅执行 Vite 构建。模拟桌面接口能够直接返回重命名成功，无法发现真实命令没有注册。

另外，锁文件将依赖地址固定到 `registry.npm.wps.cn` 的下载路径；此前本机干净安装失败，改用 npm 公共源且不改锁文件后才完成安装。这是安装可复现性问题，不能据此断言所有 CI 环境都会失败。

建议：把现有 JS 测试、类型检查纳入 CI，增加少量真实命令契约与 IPC 场景测试，整理可公开复现的依赖锁文件。优先测试用户结果，而非重复测试组件内部实现。

## 用户交互改进建议

以下是体验建议，与上面的已确认缺陷分开排期。

1. **让收集结果可以追踪。** 资源卡片明确显示“已加入队列”，并可直接定位任务；达到并发上限时显示等待位置，完成后给出文件位置。避免用户反复点击“收集”确认是否生效。
2. **批量操作保留每项结果。** 提供成功、重复、等待、失败的明细，保留原链接，支持只重试失败项。批量添加部分成功就关闭对话框，会让剩余问题难以处理。
3. **给暂停、排队和等待重试独立含义。** 显示排队原因和重试倒计时；用户主动暂停后不会再自动开始。错误说明给出可执行的下一步，例如刷新签名链接、检查目录或修正代理。
4. **区分空列表与读取失败。** 首次列表读取异常当前会结束加载并静默显示空内容。应提供“连接失败 / 重试”，筛选无结果则提供清除筛选，首次使用才显示收集引导。
5. **文件丢失时说明实际情况。** 当前打开找不到的文件会退回目录；应提示文件已移动或删除，提供打开目录、重新定位或重新下载。
6. **文章编辑提供恢复和预览。** 增加本地草稿恢复、未保存离开提醒、同步前预览；分别展示平台支持草稿还是直接发布，避免同一个开关在不同平台产生不同预期。
7. **设置使用用户熟悉的单位。** 限速以 KB/s、MB/s 输入并立即展示含义；连接诊断给出主程序未启动、扩展宿主未注册等具体状态。工具路径和底层参数继续收在高级选项。
8. **统一各端操作反馈。** 桌面、弹窗和悬浮入口共享状态名称、错误解释和打开可执行文件的确认规则。既有纸色、墨绿和字体体系可以继续使用，重点打磨反馈和节奏。
